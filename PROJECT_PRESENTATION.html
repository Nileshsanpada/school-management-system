1. Executive Summary & Objective

EduCore SMS is an enterprise-grade School Management System architected to streamline administrative workflows, academic hierarchy, duplicate-safe daily attendance, examination auto-grading, fee installment tracking, and secure parent engagement.

Dual-Portal Architectural Philosophy:
  • School Administration & Faculty Portal: Managed by School Staff (Admins & Teachers) for admissions, class structures, examinations, student records, and billing.
  • Parent Engagement Portal: Accessible by Parents to monitor live attendance %, exam performance report cards, and fee payment receipts for their linked children in strict isolation.

3. Comprehensive Module Breakdown

Module 1: Admission Management Pipeline

  • Public Webform Capture: Potential leads and parents submit admission enquiries without requiring preliminary login (captured as NEW).
  • Evaluation & Follow-up: Admission team reviews, schedules interviews, and updates status (UNDER_REVIEW, CONFIRMED, REJECTED).
  • Automated Student Onboarding: Upon confirmation, the system triggers the StudentIdGenerator to create unique identifiers (e.g. STU-2026-0001), creates student profile, links class/section, and automatically associates/creates the parent login record.

Module 2: Academic Hierarchy & Faculty Assignment

  • Hierarchy: Academic Year ➡️ Class (e.g., Class 10) ➡️ Sections (A, B) ➡️ Subjects (MATH101, SCI102).
  • Faculty Master: Teachers with employee IDs, contact credentials, and subject-class mappings.

Module 3: Daily Attendance Tracking & Low Attendance Defaulter System

  • Daily Class Roster: Teachers select date, class, and section to record bulk attendance (PRESENT, ABSENT, LATE).
  • Duplicate Entry Prevention: Database unique constraint on (student_id, attendance_date) prevents duplicate entries on the same date.
  • Low-Attendance Defaulter Warning: Automated background calculation alerts faculty and parents whenever a student's cumulative attendance drops below the statutory 75% threshold.

Module 4: Examinations & Automated Grading Engine

  • Exam Scheduling: Term exams mapped to classes and academic years.
  • Subject-Wise Results Entry: Teachers enter raw marks obtained against maximum marks.
  • Automated Grading Logic:
    • ≥ 90% ➡️ A+
    • ≥ 80% ➡️ A
    • ≥ 70% ➡️ B+
    • ≥ 60% ➡️ B
    • ≥ 50% ➡️ C
    • < 50% ➡️ F (Fail)

Module 5: Fee Structures & Multi-Installment Collections

  • Fee Invoicing: Invoices generated with total amount, academic year, and due dates.
  • Multi-Installment Payments: Payments recorded with methods (UPI, CARD, CASH, NET_BANKING) and transaction reference IDs.
  • Automated Lifecycle Transitions:
    • Paid == Total ➡️ PAID
    • 0 < Paid < Total ➡️ PARTIAL
    • Paid == 0 && DueDate < Today ➡️ OVERDUE

Module 6: Parent Portal & Child Data Isolation Security

  • Data Isolation Architecture: Security interceptor resolves parent's authenticated email from JWT token ➡️ verifies parent_id == student.parent_id. Parents are strictly prevented from viewing other students' data.
  • Multi-Child Support: Parents with multiple enrolled children can seamlessly switch profiles from a single login.
  • Real-time Progress: Live Circular Attendance Gauge, Subject Report Cards, and Official Fee Invoices with ₹ INR formatting.

5. Interviewer Q&A — Master Explanation Guide

Q1: How would you describe the overall architecture of this project?
"EduCore SMS is built on a 3-tier enterprise architecture. The frontend is a single-page application built with React and Vite featuring Light and Dark modes. The backend is a Spring Boot application running on Java 18, structured into Controller, Service, DTO, Repository, and Entity layers. Security is enforced via Spring Security with stateless JWT authentication and role-based authorization for Admin, Teacher, and Parent personas. Data persistence is managed by Spring Data JPA and Hibernate with a MySQL 8 relational schema."
Q2: Why did you create a separate Parent account instead of just Student logins?
"In school education, students are minors while parents hold legal guardianship and financial responsibility for paying tuition fees. Architecting a dedicated Parent entity with a 1-to-Many relationship to students allows a single parent (e.g. parent@school.com) with multiple children (e.g. Class 10 and Class 6) to monitor progress and pay fees for both children from one unified portal without multiple logins."
Q3: How do you guarantee that Parents cannot access other students' records?
"Every parent portal request goes through ParentController, which extracts the parent's email directly from the validated Spring Security SecurityContextHolder. The service layer executes parentService.verifyParentOwnership(userId, studentId), checking that the requested student belongs to the parent's linked ID before returning attendance, results, or fee data. If not matched, a 403 Forbidden / Access Denied exception is thrown."
Q4: How did you implement duplicate-safe Attendance and the Low Attendance Warning?
"At the database level, we enforce a composite unique constraint on (student_id, attendance_date). In the service layer, existsByStudentIdAndAttendanceDate() validates the submission before persisting. For the Low Attendance warning, the service calculates (presentDays / totalDays) * 100. If below the 75% configurable threshold, the student is flagged as a defaulter and highlighted on the Executive Dashboard."
Q5: How does the Fee Management & Payment lifecycle work?
"When a fee invoice is generated, it starts with an outstandingAmount = totalAmount. When payments are recorded in the PaymentService inside a transactional block (@Transactional), the paid amount is aggregated. If amountPaid == totalAmount, the fee status automatically transitions to PAID. If partially paid, it becomes PARTIAL. If overdue, it transitions to OVERDUE."
Q6: What technical challenges did you solve during development?
"Key challenges included: 1. CORS & Dynamic Ports: Replaced static origin strings with setAllowedOriginPatterns('*') to support multi-port frontend servers. 2. Jackson Cyclic References: Added @JsonIgnore on parent-child bidirectional relations to prevent infinite recursion during JSON serialization. 3. Data Seeding Idempotency: Built a safe DataInitializer using orElseGet() lookups to guarantee smooth startup without constraint conflicts. 4. Modern UI / Theme Engine: Built custom CSS variables for instant Light/Dark mode transitions with zero external CSS framework overhead."
